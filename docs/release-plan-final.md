### 2. النسخة الاحتياطية (من كود master الحالي، قبل الدمج)
**مهم:** شغّلها من `c015839`. الكود الجديد يصدّر جداول 0027 غير الموجودة بعد في الإنتاج، فتصبح نتيجته «ناقصة».

```bash

cd ../alsultan-release-backup/web && npm ci
# انسخ يدوياً .env.staging.app.local خارج Git

```

**التحقق:**
- آخر سطر `RESULT: COMPLETE`.
- وجود `VERIFY.txt`، وعدد الملفات مطابق.
- اقرأ سجل `supabase_migrations.schema_migrations` بوسيلة اتصال إدارية مصرح بها للقراءة، أو `supabase migration list --linked` بعد الربط الصريح. احفظ قائمة الإصدارات كاملة، لا `max(version)` فقط. المتوقع انتهاء السجل عند ملف 0025؛ إن اختلف، أوقف التنفيذ وأعد المقارنة.
- انسخ المجلد إلى قرص خارجي. فيه بيانات عملاء: لا يُرفع إلى Git ولا يُستخدم في الاختبارات.
- `npm run backup` ينسخ بيانات المستخدمين الوصفية فقط، بلا hashes كلمات المرور أو أسرار MFA. عبارة `RESULT: COMPLETE` تعني اكتمال محتويات هذا التصدير، ولا تثبت استعادة الحسابات.

**نسخة قاعدة البيانات الإضافية والتحقق منها (خطوة لازمة قبل الترحيل):**
- استخدم إجراء dump الموثق في [backup-restore.md](backup-restore.md)، من اتصال الإنتاج الصحيح وبأداة متوافقة مع إصدار PostgreSQL المصدر.
- يجب أن تشمل بيانات التطبيق و`auth.users` و`auth.identities` و`auth.mfa_factors`، مع سجل الترحيلات ومخطط التطبيق اللازم للاستعادة. لا تكتفِ بتصدير `public` وحده.
- ملفات التخزين الفعلية تُنسخ وتُفحص منفصلة؛ dump قاعدة البيانات ليس نسخة من الصور. تحقّق من metadata الحاويات والكائنات ومن hashes الملفات.
- احفظ manifest بالأعداد وSHA-256 ووقت النسخ ومرجع المشروع، وتحقق من أن dump يحتوي الأقسام المطلوبة دون طباعة صفوف Auth أو أسرارها في السجلات.
- احتفظ بالنسخة مشفّرة خارج Git. إعدادات Auth والـ redirects وSMTP ومتغيرات Vercel ومفاتيح Vault ليست مضمونة بمجرد نسخ جداول Auth؛ وثّق طريقة استعادتها بصورة منفصلة وآمنة. لا تُصدّر أسراراً إلى التقرير.
- لا تسمِّ النسخة «استعادة مجرّبة» ما لم تُحمّل فعلياً في بيئة استعادة منفصلة ومقيّدة وبإذن خاص لبيانات العملاء؛ لا تستخدم بيئة الاختبارات المعتادة ولا القاعدة المشتركة. افصل اختبار البيانات والعلاقات والصلاحيات والتخزين عن اختبار دخول حساب تجريبي معزول، ولا تسجّل الدخول بكلمات مرور العملاء.
- **الحالة الحالية:** لا توجد أدلة حديثة على تجربة استعادة هذه النسخة مع 0026–0031. إذا تعذر التحقق من قابلية استعادة النسخة، سجّل ذلك كشرط إصدار غير مكتمل، لا كنتيجة ناجحة.

### 4. Migrations
استخدم مجلد إصدار جديداً من SHA الدمج النهائي، ولا تعتمد على مسار العمل المتبقي من خطوة النسخ الاحتياطي:
```bash
# من جذر نسخة المستودع الأصلية، بعد الدمج المعتمد
git worktree add --detach ../alsultan-release <SHA-master-النهائي>
cd ../alsultan-release/web
npm ci
npx supabase --version
npx supabase link --help
npx supabase migration list --help
npx supabase db push --help
npx supabase link --project-ref dyuixzxmmeiypvawzmty
```
لا تطبع كلمات المرور ولا تمررها حرفياً في سجل الأوامر. تأكد من دعم الأعلام في إصدار CLI المثبت قبل استعمالها.

**حارس الهدف، قبل كل dry-run أو push ومن نفس مجلد web:**
```bash
node --input-type=module -e 'import fs from "node:fs"; const expected = "dyuixzxmmeiypvawzmty"; const actual = fs.readFileSync("supabase/.temp/project-ref", "utf8").trim(); if (actual !== expected) { console.error("Wrong linked project; refusing release"); process.exit(1); } console.log("Project ref verified:", actual);'
```
يجب نجاح الحارس؛ لا تتابع عند غياب الملف أو اختلاف المرجع. مجلد `supabase/.temp` مستثنى من Git ولا ينتقل تلقائياً إلى worktree جديد. طابق أيضاً المشروع في لوحة Supabase واتصال قاعدة البيانات المستخدم لقراءة السجل. لا تغيّر ربط نسخة عمل أخرى.

```bash
npx supabase migration list --linked
npx supabase db push --linked --dry-run
```
قارن السجل الموثوق وخطة dry-run بالملفات: المتوقع 0026–0031 فقط. أوقف التنفيذ عند أي ترحيل زائد أو ناقص أو سجل مختلف؛ لا تستعمل `migration repair` لتجاوز الاختلاف.
بعد اعتماد المقارنة، أعد حارس الهدف أعلاه مباشرة ثم:
```bash
npx supabase db push --linked
```
ممنوع `db reset`، محلياً على القاعدة المشتركة أو مع `--linked`.

**التحقق بعد التطبيق:**
```sql
select max(version) from supabase_migrations.schema_migrations;      -- 20261030000031
select count(*) filter (where published_at is not null) from public.photo_albums;   -- 0 قبل أي نشر جديد
select hero_cover_source from public.business_settings;              -- manual
select status from public.meta_page_connection;                      -- لا صفوف
select name from vault.secrets where name in ('facebook_jobs_url', 'meta_page_token');  -- لا صفوف
```
والموقع الحالي يبقى يعمل: الرئيسية، ألبوم، `/p`.

تحقق أن Git integration لا ينشر تلقائياً بمجرد الدمج قبل الترحيلات؛ إذا كان مفعّلاً فاضبط تسلسل الإصدار المعتمد قبل الدمج.


لا تضف `REELS_VIEWER`، ولا أي متغير لفيسبوك. لا حاجة لمتغيرات جديدة.

### 6. الفحص بعد النشر
- الرئيسية: الألبومات بترتيب `listed_at`، والخلفية لم تتغير.
- صفحة عرض وباقة: النص كامل، على الموبايل والكمبيوتر.
- `/p/<id>/display`: رأس `private, no-cache`.
- في الإدارة، بمسودة خاصة: نشر، تغيير غلاف، إخفاء، ثم تأكد أن الصورة تعطي 404 والمسودة اختفت.
- `/admin/settings/facebook` تعرض «غير مربوط». ولا يظهر زر العرض العمودي في البروموهات.
- من جذر worktree الإصدار: `node web/scripts/seo-check.mjs https://sultan-records.vercel.app`.
- بيانات الاختبار: استخدم محتوى اصطناعياً في ألبوم مسودة خاص فقط؛ أي اختبار نشر معتمد يحتاج التحقق من الخصوصية والتنظيف، ولا تُغيّر ألبومات العملاء.

**معيار قرار الرجوع:** أخطاء 5xx أو تعطل الإدارة بعد النشر تستدعي تقييم رجوع التطبيق للنشر المتحقق منه مع إبقاء القاعدة، ثم فحصه. حادث خصوصية يتطلب معالجة الوصول والكاش تحديداً، مع مراعاة قيد 300 ثانية أعلاه. ترتيب غير مرغوب فقط يُعالج بقرار المالك، ولا يستدعي استعادة القاعدة.
